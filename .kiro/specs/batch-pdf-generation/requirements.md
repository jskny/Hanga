# 要件定義書: バッチでの帳票PDFの一括生成

## はじめに

Webアプリとは別の実行ファイル(バッチ)の中で、帳票のビュー(`.cshtml`)とモデルから、帳票PDFを1件ずつファイルに保存する機能を定義する。

バッチは、アプリケーションサーバー(Webアプリ)にアクセスしない。自動テストのようにブラウザで画面を開いて操作するものでもない。
Hangaが、ビューを描画する仕組み(ASP.NET Core MVC のビュー描画)と、HTMLをPDFにする仕組み(ヘッドレスChromium)を、バッチのプロセスの中に用意する。
バッチは、帳票に載せる値をモデルとして用意し、ビュー名とモデルと保存先をHangaに渡す。

中核機能(`.kiro/specs/view-pdf-generation/`)の部品(ビューのHTML化・ページの表示・待機・外字・体裁・PDF化・例外と警告)をそのまま使う。
本書は、バッチで使うために加える・変える点だけを定める。方針は `.kiro/steering/`、方式の根拠は `docs/PDF出力方式検証レポート.md`「6.4」「6.5」を参照。

### 前提(利用部門の回答。2026年10月4日)

- **バッチはWebアプリとは別の実行ファイルにする。** 帳票のビューと静的ファイル(CSS・JavaScript・画像)は、Razor クラスライブラリにまとめ、Webアプリとバッチの両方から参照する形を推奨する。
- **PDFは1件ずつファイルに保存する。** 複数の帳票を1つのPDFに結合しない。
- **性能はベストエフォートとする。** 数値目標は持たず、そこそこの速度が出るようにする(Chromiumの使い回しと並行処理)。
- **失敗した帳票の扱い(飛ばして続けるか、全体を止めるか)はバッチ側が決める。** Hangaは、1件ごとに原因の分かる例外を返し、1件の失敗が後の帳票に影響しないことを保証する。

### 対象外

- 複数の帳票の結合、失敗時の再試行、進捗の表示、ジョブの管理・スケジュール。バッチ側の責務とする。
- Webアプリの画面を開いてPDFにする方式(アプリケーションサーバーへのアクセス)。
- バッチの中での、オペレーターに依存する情報の利用(ログインユーザー・セッション・Cookie・認証が必要なAPI)。バッチにはオペレーターがいないため。
  バッチで使う帳票のビューは、表示に必要な値をすべてモデルから受け取る作りにする(`tech.md`「外部リソースとサーバーへの要求の扱い」)。
- Razor Pages、信頼できない第三者が書いたビューの実行(中核機能と同じ)。

## 用語

中核機能の要件定義書の用語に加えて、次を使う。

- **バッチ**: 呼び出し元プロダクトの、Webアプリとは別の実行ファイル(.NET 5 のコンソールアプリ)。Hangaを参照し、帳票PDFを一括で生成する。
- **帳票ライブラリ**: 帳票のビューと静的ファイルをまとめた Razor クラスライブラリ。Webアプリとバッチの両方が参照する。
- **バッチ用の変換器**: バッチの中で、ビューの描画の仕組みとChromiumを持ち、複数の帳票で共有する部品(名称は design.md で決める)。
- **静的Webアセット**: Razor クラスライブラリの `wwwroot` のファイル。参照する側のアプリでは `/_content/<ライブラリ名>/` の下のURLで使う(ASP.NET Core の仕組み)。

## 要件

### 要件 1: バッチ用の変換器の起動と終了

**ユーザーストーリー:** バッチの開発者として、Webサーバーを立てずに、バッチの中でビューからPDFを作る準備をしたい。それは、アプリケーションサーバーに頼らずに帳票を一括で作るためだ。

#### 受け入れ基準

1. WHEN バッチがバッチ用の変換器を起動する THEN システムは ビューの描画と静的ファイルの応答に必要な ASP.NET Core MVC の仕組みを、Webサーバーを起動せず(ポートを開かず)に、バッチのプロセスの中に用意する SHALL。
2. システムは アプリ全体の設定(Chromiumの場所・同時に処理する帳票の数・待機の上限時間・外字用フォント・厳格な扱いなど)に、Webアプリと同じ設定の型を使う SHALL。設定は、コードと設定ファイルのどちらからも指定できる SHALL。
3. WHEN バッチ用の変換器を起動する THEN システムは Chromiumを起動する SHALL。IF Chromiumを起動できない、または設定に誤りがある THEN システムは 帳票の生成を始める前に、原因を含むエラーを返す SHALL。
4. WHEN バッチがバッチ用の変換器を終了する THEN システムは Chromiumのプロセスを終了し、作った一時フォルダを削除する SHALL。
5. システムは バッチ用の変換器をスレッドセーフにし、1つを共有して、複数の帳票を並行して生成できるようにする SHALL。帳票1件ごとの入口は、Webアプリと同じ簡易API(`Cshtml2Pdf`)とする SHALL。

### 要件 2: 帳票ビューのHTML化

**ユーザーストーリー:** バッチの開発者として、Webアプリの画面と同じ書き方の帳票ビューを、バッチでもそのまま使いたい。それは、画面とバッチで帳票を二重に作らないためだ。

#### 受け入れ基準

1. WHEN ビュー名とモデルが指定される THEN システムは 帳票ライブラリ(または呼び出し元が指定したアセンブリ)のビューを、画面と同じ規則(`_ViewStart.cshtml` によるレイアウトの適用、`_ViewImports.cshtml`、部分ビュー、セクション、`~/` のパスの解決、タグヘルパー)でHTMLにする SHALL。
2. システムは 呼び出し元が、ビューを持つアセンブリを指定できるようにする SHALL。指定されたアセンブリに関連するビューのアセンブリ(`<名前>.Views.dll`)も含める SHALL。
   指定が無い場合は、ASP.NET Core MVC の既定の規則(バッチの実行ファイルが参照するライブラリ)でビューを探す SHALL。
3. WHEN 帳票1件を生成する THEN システムは 呼び出し元から、ビューを探すときのコントローラー名・ビュー名(または `~/Views/...cshtml` の形のパス)・モデルを受け取る SHALL。
4. システムは 帳票1件ごとに、独立した `HttpContext` と依存性注入のスコープを作り、帳票の間で共有しない SHALL。`HttpContext` のスキームとホストには、仮想オリジンの値を使う SHALL。
5. システムは 呼び出し元が、ビューが使うサービス(`@inject`)などを、バッチ用の変換器の依存性注入に登録できるようにする SHALL。
6. IF ビューが見つからない、またはビューの描画中に例外が発生した THEN システムは 中核機能の要件1.4・1.5と同じエラーを返す SHALL。

### 要件 3: 静的ファイルと仮想オリジンへの要求

**ユーザーストーリー:** バッチの開発者として、帳票ビューが読み込むCSS・JavaScript・画像が、画面と同じようにPDFに反映されてほしい。それは、画面とバッチでPDFの見た目が食い違わないようにするためだ。

#### 受け入れ基準

1. WHEN Chromiumが仮想オリジンに要求を出す THEN システムは その要求を、バッチ用の変換器がバッチのプロセスの中に用意したパイプラインにプロセス内で渡す SHALL。ネットワーク(ソケット)を使わない SHALL。
2. システムは 帳票ライブラリの静的Webアセットを、Webアプリと同じURL(`/_content/<ライブラリ名>/...`)で応答する SHALL。
   発行(`dotnet publish`)したバッチでは発行先の `wwwroot` から、開発中の実行(ビルドの出力からの実行)では ASP.NET Core の静的Webアセットの一覧から、ファイルを探す SHALL。
3. システムは 呼び出し元が、静的ファイルを置くフォルダ(Webルート)と、URLのパスとフォルダの対応を追加で指定できるようにする SHALL。IF 指定したフォルダが存在しない THEN システムは 起動時にエラーを返す SHALL。
4. WHEN パイプラインに要求を渡す THEN システムは 認証情報(`Cookie` ヘッダー等)を付けない SHALL。
5. IF 仮想オリジンへの要求の応答が失敗(状態コード400以上)、またはリダイレクトである(存在しないファイル・認証が必要なAPIへの要求を含む) THEN システムは 中核機能の要件3.5と同じく、PDFを出力せずにエラーを返す SHALL。
6. システムは 外部への要求の遮断(中核機能の要件3.4・3.6)、表示の完了の待機(要件4)、用紙と体裁(要件5)、外字・異体字(要件6)、警告と厳格な扱い(要件8.6・8.7)を、Webアプリの場合と同じく扱う SHALL。

### 要件 4: 保存と失敗の扱い

**ユーザーストーリー:** バッチの開発者として、帳票を1件ずつファイルに保存し、失敗した帳票はバッチ側の方針で扱いたい。それは、失敗の扱い(飛ばす・止める・やり直す)が業務によって異なるためだ。

#### 受け入れ基準

1. システムは 帳票1件ごとに、PDFを、バイト列・ストリームへの書き込み・ファイルへの保存のいずれでも受け取れるようにする SHALL(中核機能の要件7.1)。
2. WHEN PDFをファイルに保存する THEN システムは 保存先と同じフォルダの一時ファイルに書き終えてから、保存先の名前に変える SHALL。
   IF 生成・書き込みの途中で失敗した、または取り消された THEN システムは 保存先にファイルを作らず(既にあるファイルを壊さず)、一時ファイルを残さない SHALL。
   この扱いは、Webアプリで使う場合のファイルへの保存にも適用する SHALL。
3. システムは 失敗した帳票を飛ばして続けるか、全体を止めるかの方針を持たない SHALL。帳票1件ごとに、失敗の段階と原因の分かる例外(中核機能の要件8)を返し、扱いは呼び出し元に任せる SHALL。
4. IF 帳票1件の生成が失敗した(ビューの例外・応答の失敗・タイムアウト・Chromiumのプロセスの終了を含む) THEN システムは 後の帳票の生成に影響させない SHALL(ブラウザコンテキストの破棄と、Chromiumの起動し直し。中核機能の要件9.2・9.5)。
5. IF 呼び出し元が処理を取り消した(`CancellationToken`) THEN システムは 処理を中止し、使っていたブラウザコンテキストを破棄する SHALL。

### 要件 5: 性能

**ユーザーストーリー:** バッチの運用担当者として、多数の帳票を、実用的な時間で生成したい。

#### 受け入れ基準

1. システムは Chromiumのプロセスを、帳票ごとに起動せず、バッチ用の変換器の起動から終了まで使い回す SHALL。
2. WHEN 呼び出し元が複数の帳票を並行して生成する THEN システムは 同時に処理する帳票の数を、設定の上限(中核機能の要件9.4)に収める SHALL。
3. システムは 性能の数値目標を持たない(ベストエフォート)。design.md で、1件ずつ順に生成した場合と並行して生成した場合の、1件あたりの時間の目安を計測して記録する SHALL。

### 要件 6: 技術的な制約

**ユーザーストーリー:** 呼び出し元プロダクトの開発者として、今の開発環境・実行環境のまま、バッチでもHangaを使いたい。

#### 受け入れ基準

1. システムは `net5.0` をターゲットとし、C# 9.0 の構文の範囲で書く SHALL。Visual Studio 2019 でビルドできる SHALL。新しい依存ライブラリを加えない SHALL。
2. システムは Windows Server 上の、Webサーバーを持たないコンソールアプリ(タスクスケジューラなどから起動する)の中で動く SHALL。Docker を前提としない SHALL。
3. システムは バッチ用の公開APIに、PuppeteerSharp の型を露出させない SHALL。
4. システムは Webアプリで使う機能(`AddHanga`・PDF用アクション)の動作を変えない SHALL(要件4.2 のファイルへの保存の改善を除く)。
5. システムは 帳票ライブラリの作り方(Razor クラスライブラリの設定)、バッチの実行ファイルの作り方(使うSDK)、オペレーターに依存する情報を使えない制約を、呼び出し元の開発者向けの文書(`docs/ライブラリの使い方.md`)に記載する SHALL。
