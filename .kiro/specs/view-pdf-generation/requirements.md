# 要件定義書: ASP.NET Core MVC のビューからのPDF生成

## はじめに

呼び出し元の ASP.NET Core MVC アプリが持つビュー(`.cshtml`)を、(1) 画面と同じ仕組みでHTMLにし、
(2) ヘッドレスChromiumで、ビューが読み込むスタイル・スクリプト・APIからの値を反映させたうえで、
(3) 商用ライブラリおよびOffice Interopに依存しない方法でPDFとして出力する機能を定義する。

主な使い方は、呼び出し元アプリのコントローラーにPDF用のアクションを追加し、オペレーターがそれを呼ぶと、
画面と同じビューをPDFにしたものを受け取る、というものである(ブラウザのPDF印刷が使えない環境での代用)。

方針・採用技術の根拠は `.kiro/steering/`(特に `tech.md`「採用技術」)と `docs/PDF出力方式検証レポート.md` を参照。

### この版の対象外

- **バッチ(HTTPリクエストの外)での一括生成**: 実現できることは検証済み(検証レポート「6.4」)だが、要件化は次回以降に行う。
  本書の要件は、バッチへの拡張を妨げない形にする(要件1.6)。
- Razor Pages(`@page` ディレクティブを持つページ)。利用部門の画面はMVCのビューであるため。
- 信頼できない第三者が書いたビューの実行(`.kiro/steering/product.md`「非対応」)。

## 用語

- **呼び出し元アプリ**: Hangaを参照する ASP.NET Core 5 の MVC アプリ。帳票のビュー・静的ファイル・APIを持つ。
- **帳票ビュー**: PDFにする対象のビュー。画面用のビューと同じもの(レイアウト `_Layout.cshtml`、`ViewData`、`~/` のパス、タグヘルパーを含みうる)。
- **元の要求**: オペレーターのブラウザから呼び出し元アプリへの、PDF用アクションのHTTP要求。
- **仮想オリジン**: Hangaが帳票ビューのページを置く、実在しないオリジン(例: `https://hanga.invalid`)。このオリジンへの要求は、ネットワークに出ない。
- **パイプライン**: 呼び出し元アプリのミドルウェアのパイプライン(`Startup.Configure` 等で組み立てたもの)。
- **外字用フォント**: 帳票の本文フォントに字形の無い文字(JIS第4水準の外の人名用漢字など)や異体字を描くためのフォント(IPAmj明朝など)。
- **変換器**: Chromiumのプロセスなどの重い資源を持ち、複数の要求で共有する部品。
- **簡易API**: Utsushi の `Excel2Pdf` に相当する、帳票1件ごとに作って使う入口(名称は design.md で決める。仮称 `Cshtml2Pdf`)。

## 要件

### 要件 1: 帳票ビューからのHTMLの生成

**ユーザーストーリー:** 呼び出し元アプリの開発者として、画面用に書いた既存のビューを、書き換えずにそのままPDFの元にしたい。それは、帳票ごとにPDF専用のテンプレートを作る手間を省くためだ。

#### 受け入れ基準

1. WHEN ビュー名とモデルが指定される THEN システムは 呼び出し元アプリの ASP.NET Core MVC のビュー描画の仕組み(`IRazorViewEngine`)で、画面を表示するときと同じ規則でビューを探し、HTMLにする SHALL。
2. WHEN ビューをHTMLにする THEN システムは `_ViewStart.cshtml` によるレイアウトの適用、`_ViewImports.cshtml`、`ViewData`・`ViewBag`、セクション(`RenderSection`)、部分ビュー、`~/` のパスの解決、タグヘルパー(`asp-append-version`、`asp-controller`/`asp-action` によるURL生成を含む)を、画面と同じ結果にする SHALL。
3. WHEN PDF用アクションから呼ばれる THEN システムは 元の要求のコントローラー名を既定として使い、ビューを探す SHALL。呼び出し元は、コントローラー名を明示して別のコントローラーのビューを指定できる SHALL。
4. IF 指定されたビューが見つからない THEN システムは PDFの生成を中止し、探した場所の一覧を含むエラーを返す SHALL。
5. IF ビューの描画中に例外が発生した THEN システムは PDFの生成を中止し、元の例外を内部例外として含むエラーを返す SHALL。
6. システムは ビューのHTML化に必要な情報(`HttpContext`・ルーティング情報など)を、元の要求が無い場合にも用意できる構造にする SHALL(バッチへの拡張のため。この版では元の要求がある場合のみを対象とする)。

> 補足(要件1): テンプレート展開に RazorLight を使わない根拠は、検証レポート「6」。利用部門から提示されたビューの例(`ViewData["Title"]` を使い、レイアウトと組み合わせる形)は、RazorLight ではコンパイルできなかった。

### 要件 2: HTMLからのPDFの生成

**ユーザーストーリー:** オペレーターとして、画面に表示される内容を、そのままPDFとして受け取りたい。それは、ブラウザのPDF印刷が使えない環境で、画面の内容を帳票として残す・渡すためだ。

#### 受け入れ基準

1. WHEN 帳票ビューのHTMLができる THEN システムは ヘッドレスChromiumでそのHTMLを表示し、ChromiumのPDF出力機能でPDFを生成する SHALL。
2. システムは Chromiumの実行ファイルの場所を、呼び出し元の設定から受け取る SHALL。実行時にブラウザをダウンロードしない SHALL。
3. システムは Chromiumの操作に `PuppeteerSharp` 18.1.0 を使い、Chrome DevTools Protocol の `Page.navigate` 命令(`GoToAsync`)を使わない SHALL。
4. WHEN 帳票ビューのページを開く THEN システムは 空白のページから、ページ内のJavaScriptで仮想オリジンのURLへ移動し、その要求に対して帳票ビューのHTMLを返す SHALL。
5. システムは PDF内の文字を、文字列として検索・コピーできる形で出力する SHALL(画像化しない)。
6. システムは 呼び出し元に、PuppeteerSharp・Chromium・ASP.NET Core MVC の内部の型を、公開APIとして見せない SHALL。

> 補足(要件2.3, 2.4): PuppeteerSharp 20以降は .NET 5 を公式にサポートしない依存パッケージを連れてくるため、18.1.0 に固定する。
> 18.1.0 の `GoToAsync` は新しいChrome(141・154で確認)に `Invalid referrerPolicy` で拒否される。ページ内のJavaScriptによる移動はこの命令を使わない(検証レポート「3」「8」)。

### 要件 3: 外部リソースとサーバーへの要求

**ユーザーストーリー:** オペレーターとして、画面で表示されるスタイル・画像・フォント・JavaScriptで取得した値が、PDFにも同じように反映されていてほしい。それは、画面とPDFで内容が食い違わないようにするためだ。

#### 受け入れ基準

1. WHEN Chromiumが仮想オリジンに対して要求を出す THEN システムは その要求を、呼び出し元アプリのパイプラインにプロセス内で渡し、パイプラインの応答(状態コード・ヘッダー・本文)をChromiumに返す SHALL。ネットワーク(ソケット)を使わない SHALL。
2. WHEN パイプラインに要求を渡す THEN システムは 元の要求の `Cookie` ヘッダーを付け、APIなどがオペレーターの権限で応答するようにする SHALL。
3. WHEN パイプラインに要求を渡す THEN システムは 元の要求の `Host`・スキーム・パスベースを使い、要求ごとに独立した `HttpContext` と依存性注入のスコープを作る SHALL。
4. WHEN Chromiumが仮想オリジン以外に要求を出す THEN システムは 既定でその要求を遮断する SHALL。呼び出し元が設定で許可したホストへの要求は、ネットワーク経由で取得させる SHALL。
5. IF パイプラインの応答が失敗(状態コード400以上)、またはリダイレクト(状態コード300番台。ログイン画面への転送を含む)である THEN システムは 崩れたPDFを出力せず、要求のURLと状態コードを含むエラーを返す SHALL。
   設定で許可した外部ホストへの要求が失敗した場合(状態コード400以上、名前解決の失敗など)も同じとする SHALL。
6. IF 設定で許可していない外部への要求が遮断された THEN システムは 既定では、遮断したURLを警告として記録し(要件8.6)、PDFの生成を続ける SHALL。
   呼び出し元が設定で厳格な扱いを選んだ場合は、PDFを出力せず、遮断したURLを含むエラーを返す SHALL。
7. WHEN Chromiumが自動で行う要求(`/favicon.ico`)が出る THEN システムは パイプラインに渡さずに空の応答を返し、失敗として扱わない SHALL。
8. システムは 帳票ビューのJavaScriptが、ページの表示時に自動で行う非同期の要求(`fetch`・`XMLHttpRequest` 等)を、要件3.1〜3.5と同じく扱う SHALL。ボタン操作などの後に行う要求は対象外とする。

> 補足(要件3.1): 静的ファイル(`UseStaticFiles`)もAPIも画面と同じ処理で応答されるため、フォルダへの対応付けを別に持たない。
> HTTPで自分自身へ取りに行く方式は、ポート・HTTPS証明書・リバースプロキシの構成に左右されるため採らない(検証レポート「8」)。

### 要件 4: 表示の完了の待機

**ユーザーストーリー:** オペレーターとして、JavaScriptが値を描画し終わった状態のPDFを受け取りたい。それは、「読み込み中」のような途中の状態が帳票に残らないようにするためだ。

#### 受け入れ基準

1. WHEN 帳票ビューのページを開く THEN システムは ページの読み込み、スタイル・スクリプト・画像・Webフォントの読み込み、非同期の要求がすべて終わる(一定時間、新しい要求が出ない)まで待ってからPDFを生成する SHALL。
2. システムは 呼び出し元が、待機の完了条件として、ページ内で評価するJavaScriptの式(例: `window.reportReady === true`)を追加で指定できるようにする SHALL。
3. システムは 待機に上限時間を設ける SHALL。上限時間は呼び出し元が設定で変えられる SHALL。
4. IF 上限時間までに表示が完了しない THEN システムは PDFを出力せず、待機していた条件を含むタイムアウトのエラーを返す SHALL。
5. IF 帳票ビューのJavaScriptで捕まえられていない例外が発生した THEN システムは 既定では、その内容を警告として記録し(要件8.6)、PDFの生成を続ける SHALL。
   呼び出し元が設定で厳格な扱いを選んだ場合は、PDFの生成を中止し、エラーを返す SHALL。

### 要件 5: 用紙と体裁の指定

**ユーザーストーリー:** 呼び出し元アプリの開発者として、Utsushi の `Excel2Pdf` と同じように、用紙サイズや向きなどをオプションで指定したい。それは、画面ごとに適したPDFを出すためだ。

#### 受け入れ基準

1. システムは 用紙サイズ(A3・A4・A5・B4・B5・Letter・Legal、および幅と高さのmm指定)、向き(縦・横)、余白(上下左右、mm)を指定できる SHALL。
   指定が無い場合は A4 縦とする SHALL。呼び出し元は、オプションで横向きやほかの用紙サイズ・余白に変えられる SHALL。
2. システムは 用紙サイズを PuppeteerSharp の用紙サイズの定数(`PaperFormat`)に頼らず、mm単位の寸法で Chromium に指定する SHALL。
3. システムは 拡大縮小の倍率を指定できる SHALL。
4. システムは 「画面の幅を用紙の幅に収める」指定を持ち、有効な場合は、ページの内容の幅が印刷可能な幅を超えるときに、内容全体が収まるように縮小する SHALL。
   この指定は既定で有効とし、呼び出し元がオプションで無効にできる SHALL。
5. システムは 「画面の全体を1ページにする」指定を持ち、有効な場合は、ページの内容の高さに合わせた1ページのPDFを生成する SHALL。
6. システムは 印刷用のCSS(`@media print`)を使うか、画面表示用のCSSを使うかを指定できる SHALL。既定は印刷用のCSSを使う SHALL(ブラウザの印刷と同じ結果にするため)。
7. システムは 背景色・背景画像を出力するかを指定できる SHALL。既定は出力する SHALL。
8. システムは ページ番号(「1 / 3」の形式)をフッターに出すかを指定できる SHALL。
9. システムは PDFの文書のタイトル(文書のプロパティ)を指定できる SHALL。指定が無い場合は、ページの `<title>` を使う SHALL。

> 補足(要件5.2): `PaperFormat.A4` の高さは PuppeteerSharp の版によって約1pt異なる(検証レポート「3」)。mm指定でもChromiumの内部で丸めが入り、
> 正確なA4(595.28 × 841.89pt)にはならない(検証レポート「6.3」)。許容する誤差は design.md で定める。
>
> 補足(要件5.4〜5.6): Chromium の機能で実現できることを確認した(design.md「検証結果」)。

### 要件 6: 外字・異体字

**ユーザーストーリー:** オペレーターとして、顧客の氏名・住所に含まれる外字や異体字が、正しくPDFに出てほしい。それは、宛名などの誤りを防ぐためだ。

#### 受け入れ基準

1. システムは 外字用フォントを設定で指定できる SHALL。指定は、サーバーにインストールされたフォントの名前を基本とし、フォントファイルのパスも指定できる SHALL。
2. WHEN 外字用フォントが設定されている THEN システムは 帳票ビューのページに外字用フォントを注入し、全要素のフォント指定の末尾に加える SHALL(本文フォントに字形が無い文字だけが外字用フォントで描かれる)。
3. システムは 外字用フォントを使う文字の範囲を `unicode-range` で絞り(CJK統合漢字拡張B以降、私用領域など)、該当する文字の無いページでは外字用フォントを読み込ませない SHALL。
4. WHEN 異体字セレクタ(U+E0100〜U+E01EF)付きの文字がページにある THEN システムは その文字を外字用フォントで描く SHALL(本文フォントに基底の文字の字形があっても、異体字セレクタを無視させない)。
5. システムは 外字の扱いを、Chromium が自動で選ぶ代替フォントに頼らない SHALL(OSによって選び方が異なるため)。
6. IF 設定された外字用フォントがサーバーに見つからない THEN システムは 最初のPDFの生成を待たずにエラーを返す SHALL(フォントファイルの指定は登録時、インストール済みのフォントの名前の指定はChromiumの起動時に確かめる)。
7. IF PDFに、どのフォントにも字形が無い文字(□で描かれる文字)が含まれる THEN システムは 既定では、その文字を警告として記録し(要件8.6)、PDFを返す SHALL。
   呼び出し元が設定で厳格な扱いを選んだ場合は、PDFを出力せず、字形の無い文字を含むエラーを返す SHALL。

> 補足(要件6): 検証レポート「7」。フォントファイルを転送する方式は遅い(46MBで約5秒余分)ため、インストール済みのフォントの名前での参照(`local()`)を基本とする。
> 異体字が指定どおりの字形で描かれることは、IPAmj明朝で既定と異なる字形が割り当てられた組み合わせ(「葛」+U+E0102 等)で確認した(design.md「検証結果」)。
>
> 補足(要件6.7): 検出の方法は design.md「⑧」。判定用のフォントを使って canvas に描き比べる方式で、OSの代替フォントに左右されずに検出できることを確認した。
> この方式では、OSの代替フォントでたまたま描ける文字も「字形が無い」と判定する(要件6.5 の方針どおり、OSに頼る文字を知らせる)。

### 要件 7: PDFの返し方

**ユーザーストーリー:** 呼び出し元アプリの開発者として、PDFをブラウザで開かせることも、ダウンロードさせることもしたい。それは、画面ごとに使い勝手のよい方法を選ぶためだ。

#### 受け入れ基準

1. システムは 生成したPDFを、バイト列・ストリームへの書き込み・ファイルへの保存のいずれでも受け取れるようにする SHALL。
2. システムは PDF用アクションからそのまま返せる結果(`IActionResult`)を作れる SHALL。
3. WHEN PDF用アクションの結果を作る THEN システムは ブラウザで開く形(`Content-Disposition: inline`)と、ダウンロードさせる形(`attachment`)を選べる SHALL。
4. WHEN ファイル名が指定される THEN システムは 日本語を含むファイル名を、主要なブラウザで正しく表示されるように `Content-Disposition` に設定する SHALL(RFC 6266 / RFC 5987 の `filename*`)。

### 要件 8: エラーの扱い

**ユーザーストーリー:** 呼び出し元アプリの開発者として、PDFが作れなかったときに、原因と段階が分かる例外を受け取りたい。それは、オペレーターへの案内と、運用部門への連絡を適切に行うためだ。

#### 受け入れ基準

1. システムは Hangaが出す例外を、共通の基底クラス(仮称 `HangaException`)から派生させる SHALL。
2. システムは 例外に、失敗した段階(ビューのHTML化・Chromiumの起動・ページの表示・外部リソース・待機・PDFの出力)を持たせる SHALL。
3. IF Chromiumの起動、またはChromiumへの命令に失敗した THEN システムは Chromiumの実行ファイルの場所と版(取得できた場合)を含むエラーを返す SHALL。
4. IF APIなどの応答が失敗した(要件3.5)、または表示の完了を待ちきれなかった(要件4.4) THEN システムは 設定によらず、エラーを返す SHALL(必要な値が欠けたPDFを返さないため)。
5. システムは 例外のメッセージ・警告に、オペレーターの認証情報(`Cookie` の値等)を含めない SHALL。
6. WHEN 警告の対象となる事象(要件3.6・4.5・6.7)が起きる THEN システムは それを `ILogger` に警告として記録し、さらに呼び出し元が生成結果から警告の一覧を取得できるようにする SHALL。
7. システムは 警告の対象となる事象をエラーにする「厳格な扱い」を、変換器の設定でまとめて指定できるようにし、帳票1件ごとの設定で上書きできるようにする SHALL。既定は厳格にしない(警告にとどめる)とする SHALL。

### 要件 9: スレッドセーフと同時実行

**ユーザーストーリー:** 呼び出し元アプリの開発者として、複数のオペレーターが同時にPDFを要求しても、正しく、取り違えなく処理されてほしい。それは、他人の情報が帳票に混ざる事故を防ぐためだ。

#### 受け入れ基準

1. システムは 変換器をスレッドセーフにし、アプリ全体で1つを共有して使えるようにする SHALL。簡易APIは要求(帳票1件)ごとに作る部品とし、スレッドセーフでないことを明記する SHALL。
2. WHEN 帳票1件を処理する THEN システムは 独立したブラウザコンテキストを作り、処理が終わったら破棄する SHALL(帳票の間で、Cookie・localStorage・キャッシュなどを共有しない)。
3. システムは 元の要求から必要な値(`Cookie` ヘッダー等)を処理の開始時に写し取り、Chromiumからの要求の処理(別のスレッドで動く)で元の要求の `HttpContext` を直接参照しない SHALL。
4. システムは 同時に処理する帳票の数に上限を設け、超えた要求は待たせる SHALL。上限の既定は4とし、呼び出し元が設定で変えられる SHALL。
5. IF 共有しているChromiumのプロセスが終了していた THEN システムは 排他制御のうえで1回だけ起動し直し、処理を続ける SHALL。
6. IF 呼び出し元が処理を取り消した(`CancellationToken`。オペレーターがブラウザを閉じた場合を含む) THEN システムは 処理を中止し、使っていたブラウザコンテキストを破棄する SHALL。

> 補足(要件9): リクエストごとにChromiumを起動する検証コードで、8人の同時要求で値の取り違えが無いことを確認した(検証レポート「8.4」)。

### 要件 10: 性能

**ユーザーストーリー:** オペレーターとして、PDFを待たされる時間をできるだけ短くしたい。

#### 受け入れ基準

1. システムは Chromiumのプロセスを、帳票ごとに起動せず、使い回す SHALL(要件9.2 のとおり、帳票ごとに分けるのはブラウザコンテキストとする)。
2. システムは Chromiumのプロセスを、最初のPDFの要求時に起動する SHALL。呼び出し元は、アプリの起動時にあらかじめ起動しておくこともできる SHALL。
3. システムは 外字用フォントを、インストール済みのフォントの名前で参照できる場合はファイルを転送しない SHALL(要件6.1)。
4. システムは 性能の数値目標を持たない(ベストエフォート)。design.md で、1件あたりの時間の目安を計測して記録する SHALL。

### 要件 11: Chromium のバージョンアップへの備え

**ユーザーストーリー:** 運用部門の担当者として、Chromiumをバージョンアップする前に、帳票が正しく出力されることを確かめたい。それは、脆弱性対応のためのバージョンアップで、帳票の出力が止まったり崩れたりする事故を防ぐためだ。

#### 受け入れ基準

1. システムは 指定したChromiumで、サンプルの帳票をPDFにし、前回の結果と比べる検証ツールを提供する SHALL。
2. WHEN 検証ツールで比べる THEN システムは ページ数・ページサイズ・取り出した文字列・ページを画像にした結果を比べ、違いがあれば一覧にする SHALL。
3. システムは Chromiumの版を、変換器の作成時(またはChromiumの起動時)に記録する SHALL。
4. システムは 検証ツールの使い方を、運用部門向けの文書(`docs/`)にする SHALL。

### 要件 12: 技術的な制約

**ユーザーストーリー:** 呼び出し元アプリの開発者として、Hangaを今の開発環境・実行環境のまま使いたい。

#### 受け入れ基準

1. システムは `net5.0` をターゲットとし、C# 9.0 の構文の範囲で書く SHALL。Visual Studio 2019 でビルドできる SHALL(`.kiro/steering/tech.md`)。
2. システムは 商用ライブラリと Office Interop を使わない SHALL。依存ライブラリは MIT / Apache-2.0 / BSD 等の無償OSSライセンスに限る SHALL。
3. システムは .NET 5 を公式にサポートしない依存パッケージを連れてくるライブラリを使わない SHALL(呼び出し元アプリの `System.Text.Json`・`Microsoft.Extensions.*` を置き換えないため)。
4. システムは Windows Server 上で、IIS からリバースプロキシされた Kestrel のアプリの中で動く SHALL。Docker を前提としない SHALL。
5. システムは 呼び出し元アプリに、Hangaのサービスを登録する手段(`IServiceCollection` への登録、パイプラインを捕まえる `IStartupFilter` の登録を含む)を提供する SHALL。
6. システムは アプリ全体の設定(Chromiumの場所、同時に処理する帳票の数、待機の上限時間、外字用フォント、厳格な扱いなど)を、コードと設定ファイル(`appsettings.json`)のどちらからも指定できるようにする SHALL。
   設定ファイルの値は、アプリの再起動で反映する SHALL。
