# 開発環境メモ(Claude Code on the web実行環境)

対象読者: このリポジトリで作業するAIエージェント(Claude Code)本人。ローカル開発機やCI環境には基本的に当てはまらない。

本メモは、同じ実行環境で開発している姉妹プロダクト Utsushi(Excel帳票→PDF変換ライブラリ。`jskny/Utsushi`)の
`docs/開発環境メモ.md` を出発点にしている。記載の出典は次の3種類に分け、各項目にどれに当たるかを示す。

- **[Hanga確認]** Hangaのセッション上で実際にコマンドを実行して確認した内容(確認日を併記する)
- **[Utsushi確認]** Utsushiのセッションで実機確認された内容。実行環境が共通のため引き継いでいるが、Hangaでは未再検証
- **[参考]** 公式ドキュメント等に基づく記載で、実機では未検証

実装作業中に環境起因の疑わしい挙動に遭遇したら、まず本書の該当節を確認すること。
新たに確認した事実があれば追記し、[Utsushi確認] の項目をHangaで再確認できたら [Hanga確認] に改めること。

## 1. .NET SDK

- このセッションには `dotnet` コマンドはプリインストールされていない(`command not found`)。都度セットアップが必要。[Hanga確認 2026-10-03]
- このセッションのapt標準リポジトリ(Ubuntu 24.04 noble)には `dotnet-sdk-8.0` と `dotnet-sdk-10.0` のみが存在し、
  `dotnet-sdk-5.0` は候補にない(`apt-cache policy` で確認)。.NET 5 はEOLのためaptから外れている。[Hanga確認 2026-10-03]
- `apt-get update` 実行時、本プロジェクトと無関係な一部PPA(`ppa.launchpadcontent.net` 上の `deadsnakes/ppa`、`ondrej/php` 等)への
  `Invalid response from proxy: HTTP/1.1 403 Forbidden` エラーが混在するが、無視してよい。
  Ubuntu本体のアーカイブの取得自体は成功しており、`apt-get install` の成否とは無関係。
  **apt-getのログにエラー文字列があるかどうかではなく、`dotnet --version`(または`command -v dotnet`)の終了コードで判断すること。** [Utsushi確認]
- `apt-get install -y dotnet-sdk-10.0` で .NET 10 SDK が入る。[Utsushi確認]

- `apt-get install -y dotnet-sdk-10.0` で .NET SDK 10.0.112 が入った。[Hanga確認 2026-10-03]

### 本物の .NET 5 ランタイムで動かす方法 [Hanga確認 2026-10-03]

`RollForward` で動かすと、実際には .NET 10 ランタイムで実行される。.NET 5 ランタイムでの動作を確かめたい場合は、
自己完結型で発行すると、NuGetから .NET 5 ランタイム(`Microsoft.NETCore.App.Runtime.linux-x64` 5.0.17。ASP.NET Coreアプリなら `Microsoft.AspNetCore.App.Runtime.linux-x64` 5.0.17 も)を取得して同梱できる。

```bash
dotnet publish -c Release -r linux-x64 --self-contained true -o <出力先>
```

- そのまま実行すると `No usable version of libssl was found` で止まる。.NET 5 は Ubuntu 24.04 の OpenSSL 3 に対応していないため。
- Ubuntu 20.04 の `libssl1.1` パッケージ(`http://archive.ubuntu.com/ubuntu/pool/main/o/openssl/libssl1.1_1.1.1f-1ubuntu2_amd64.deb`)を
  `dpkg-deb -x` で任意のフォルダに展開し、`LD_LIBRARY_PATH=<展開先>/usr/lib/x86_64-linux-gnu` を付けて実行すると動いた(システムにはインストールしない)。

### .NET 5 (net5.0) をこの環境でビルド・テストする方法

Hangaは呼び出し元プロダクトが .NET 5 であるという制約上、`net5.0` をターゲットフレームワークとする。
**.NET 5 のSDK/ランタイムを別途インストールする必要はなく、apt-getで入る `dotnet-sdk-10.0` だけで `net5.0` のビルド・`dotnet test` 実行まで行える。** [Utsushi確認]

1. **ビルド**: `<TargetFramework>net5.0</TargetFramework>` のプロジェクトは、.NET 10 SDKのままで `dotnet build` が成功する。
   `net5.0` 用の参照アセンブリはNuGetから自動的に復元されるため、SDK側に対応するランタイムが入っている必要はない。
   `warning NETSDK1138: The target framework 'net5.0' is out of support` が出るが想定通り
   (Utsushiでは `Directory.Build.props` で `<CheckEolTargetFramework>false</CheckEolTargetFramework>` として抑止している)。
2. **C#の言語バージョン**: 呼び出し元プロダクトの開発環境がVisual Studio 2019(C# 9.0までしかサポートしない)であるため、
   `<LangVersion>9.0</LangVersion>` を明示し、file-scoped namespace(`namespace Foo;`)やrecord struct等C# 10以降の構文は使わない。
   これはVS2019側の制約であり、この開発環境(Claude Code on the web)自体には起因しない。
3. **実行(テスト含む)には `RollForward` が必要**: ビルドした `net5.0` アセンブリをそのまま実行すると、
   `Framework: 'Microsoft.NETCore.App', version '5.0.0' ... The following frameworks were found: 10.0.x` というエラーで起動に失敗する。
   `.csproj` に `<RollForward>LatestMajor</RollForward>` を追加すると、インストール済みの新しいランタイムにロールフォワードして実行できる。
   `dotnet --roll-forward LatestMajor <dll>` や `DOTNET_ROLL_FORWARD=LatestMajor` でも効くが、`dotnet test` はこれらのCLIオプションを
   素直に通さないため、**`.csproj` 側に `RollForward` プロパティとして書く方法を標準にする**。[Utsushi確認]
4. **テストパッケージのバージョン**: `net5.0` + `RollForward` のxUnitテストプロジェクトは、
   `Microsoft.NET.Test.Sdk` 17.1.0 / `xunit` 2.4.1 / `xunit.runner.visualstudio` 2.4.3 の組み合わせで `dotnet test` が成功する。
   より新しい組み合わせ(`Microsoft.NET.Test.Sdk` 17.11.1 / `xunit.runner.visualstudio` 2.8.2)では「No test is available」となり
   テストが発見されなかったため、テストパッケージは net5.0世代のバージョンに合わせること。[Utsushi確認]
5. まとめると、Hangaの `.csproj`(または `Directory.Build.props`)は最低限以下を含める。
   ```xml
   <TargetFramework>net5.0</TargetFramework>
   <LangVersion>9.0</LangVersion>
   <RollForward>LatestMajor</RollForward> <!-- 実行可能プロジェクト・テストプロジェクトのみ -->
   ```

### Visual Studio 2019 でのビルド(呼び出し元プロダクトの開発環境)

- **VS2019と同じコンパイラでのビルド**: 新しいSDKのコンパイラは `LangVersion=9.0` でも細かな挙動がVS2019同梱のRoslyn 3.11と異なりうる。
  Utsushiでは `Directory.Build.props` にスイッチを設け、`Microsoft.Net.Compilers.Toolset` 3.11.0(MIT)に差し替えてビルドできるようにしている
  (`dotnet build --no-incremental -p:UtsushiVs2019Compiler=true`)。Hangaでも同じ仕組みを導入する場合の注意点: [Utsushi確認]
  - このパッケージのコンパイラは.NET Core 3.1向けだが、同梱の `csc.runtimeconfig.json` がメジャーバージョンを越えたロールフォワードを指定しているため、
    .NET 10ランタイムしか無いこの環境でも追加設定なしに動く。
  - .NET 10 SDKは既定で自前のコンパイラのパスで上書きするため、`<RoslynCompilerType>Custom</RoslynCompilerType>` が必要。
    差し替えが効いているかは `-v:n` のログに `microsoft.net.compilers.toolset/3.11.0/.../csc.dll` が出るかで確かめられる。
  - 新しいSDK同梱のアナライザーはRoslyn 3.11に読み込めず警告CS8032が大量に出るため、このモードでは `RunAnalyzers=false` にする。
  - 差し替えた後は `--no-incremental` を付けないと、前回の成果物が使われてコンパイル自体が走らないことがある。
- **.NET 5 SDKそのものは、この環境では入手できない**: `dotnet-install.sh` の取得先(`dot.net`)がプロキシで403になる。
  .NET 5 SDK 5.0.408(MSBuild 16.11 + Roslyn 3.11)でのビルドはCIのWindowsジョブで確認する(Utsushiの `.github/workflows/ci.yml` を参照)。[Utsushi確認]
- **VS2019のPCでの注意**: .NET SDK 6.0.300以降はVS 16.11以前には読み込まれない。`global.json` が無いと最も新しいSDKが選ばれるため、
  .NET 6以降のSDKも入ったPCでは、リポジトリのルート(`.sln` と同じ場所)で次のコマンドを実行して.NET 5 SDKに固定する。
  `dotnet --list-sdks` に5.0.4xxが出ることを先に確認する。[参考: Microsoft Learn「Version requirements for .NET 6 SDK」]
  ```bash
  dotnet new globaljson --sdk-version 5.0.408 --roll-forward latestPatch
  ```
  `global.json` はコミットしない(この環境とCIのLinuxジョブには.NET 5 SDKが無く、コミットすると標準のビルドコマンドが壊れるため。`.gitignore` で除外する)。

## 2. 日本語フォント(PDF出力の動作確認に必要)

- **このセッションでは日本語フォントが最初から入っていた**。`fc-list` は59件、`fc-list :lang=ja` は10件で、
  ファミリは `IPAGothic` / `IPAPGothic` / `WenQuanYi Zen Hei` 系 / `Unifont` 系。[Hanga確認 2026-10-03]
  - Utsushiのセッション(2026年9月)では初期状態の `fc-list :lang=ja` が0件だったと記録されている。
    セッション・環境のイメージによって異なる可能性があるため、**作業開始時に `fc-list :lang=ja` で確認すること**。
  - 帳票で使われがちな `MS PGothic` 等のWindowsフォントは当然存在しない。
- 日本語フォントが無い場合は、IPAフォント(IPA Font License、再配布可)を入れる。
  `apt-get install -y fonts-ipafont-gothic fonts-ipafont-mincho` で `IPAGothic` / `IPAMincho` が使えるようになる。[Utsushi確認]
- 人名用の外字(「𠮷」U+20BB7 など、JIS第4水準の外の文字)を試すときは `apt-get install -y fonts-ipamj-mincho` で
  IPAmj明朝(`/usr/share/fonts/truetype/ipamj/ipamjm.ttf`、46MB)を入れる。
  BIZ UDPゴシックは `fonts-morisawa-bizud-gothic` でインストールできる。[Utsushi確認]
- インストールしたフォントはセッションのコンテナが破棄されるまでしか保持されない。
- **太字の注意点**: IPAフォントには太字の字形が無い。SkiaSharp で書体レベルの太字合成をさせると、PDFが Type 3 フォントになり
  文字列検索ができなくなる(Utsushiは通常字形を埋め込み、描画時に輪郭を太らせることで回避している)。
  PDF出力の方式によらず、`pdffonts` の出力に `Type 3` が現れたら太字・斜体の合成が原因でないか調べること。[Utsushi確認]

### 生成したPDFの確認方法

`apt-get install -y poppler-utils` で入る以下のコマンドが使える。[Utsushi確認]

```bash
pdfinfo out.pdf                     # ページ数・ページサイズ・メタデータ
pdffonts out.pdf                    # 埋め込みフォントの種別(Type 3 か CID TrueType か)・埋め込み有無
pdftoppm -r 100 -png out.pdf page   # ページを画像化して目視確認する
```

## 4. Playwright / Chromium

HTMLからPDFを作る方式としてヘッドレスChromiumを検討する場合、この節が前提情報になる。

- Chromiumが `/opt/pw-browsers` 配下にプリインストール済みで、環境変数 `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers` が設定されている。
  `/opt/pw-browsers/chromium` の実体は `chromium-1194/chrome-linux/chrome`。ほかに `chromium_headless_shell-1194` と `ffmpeg-1011` がある。[Hanga確認 2026-10-03]
- `playwright install` は実行しないこと(再ダウンロードが走る)。利用するPlaywrightパッケージとプリインストール済みChromiumのバージョンが
  ずれて起動に失敗する場合は、プリインストール済み実行ファイルのパスを明示的に指定する
  (C#の `Microsoft.Playwright` なら起動オプションの `ExecutablePath`、PuppeteerSharpなら `LaunchOptions.ExecutablePath`)。
- **注意**: この環境にChromiumがあることは、本番サーバーにChromiumを置けることを意味しない。
  PDF出力方式の選定では、本番環境(呼び出し元プロダクトのサーバー)での配置可否を別途確認すること。

## 5. `pkill -f` / `pgrep -f` の自己マッチ問題(重要)

Bashツールに渡したコマンドは、実際には `/bin/bash -c "<渡したコマンド文字列全文>"` という形で実行される。[Utsushi確認]

このため、**`pkill -f "<パターン>"` を直接Bashツールのコマンドとして書くと、そのパターン文字列がコマンド文中に存在すること自体によって、
呼び出し元の `bash -c` プロセス自身にマッチしてしまう。** 対象プロセスが実在するかどうかに関係なく、このBashツール呼び出し自身が
SIGTERMで即座に終了し(exit code 144)、後続の行は一切実行されない。`|| true` を付けても防げない。

対策:
- Bashツールの呼び出しに `pkill -f "<パターン>"` を直接書かない。
- 対象プロセスの実行名が15文字以内であれば、`-f` を使わない `pkill <プロセス名>` を使う(完全一致検索のため自己マッチしない)。
- `-f` が必要な場合は、パターン文字列をリポジトリ内のスクリプトファイルの内部に保持し、Bashツールからはそのスクリプトを短い引数で呼び出す。

Chromiumを子プロセスとして起動する方式を試す場合、残ったブラウザプロセスの後始末で特に踏みやすいので注意すること。

## 6. Git: 指定ブランチが既にマージ済みの状態で次の増分を始める場合

このハーネスでは1つの指定ブランチを複数回のPRで使い回す。あるPRがsquash mergeされた後、同じブランチの古い先端の上に
次の増分を積むと、**見せかけのマージコンフリクト**が起きる。[Utsushi確認]

**症状**: `git push` が `(non-fast-forward)` で拒否される、またはPRの `mergeable_state` が `"dirty"` になる。
ローカルの `git diff origin/main HEAD` は意図した差分だけを示しているように見える。

**原因**: squash mergeは新しいコミットハッシュを `main` に作るため、squash元のコミットとmain上のsquash後のコミットは
内容(ツリー)が同じでも別のコミットオブジェクトになる。古い先端の上に積むと3-way mergeの共通祖先が遡ってしまい、
実際には競合しない変更同士が衝突として検出される(`tasks.md` の末尾に追記していく形式のファイルで顕著)。

**診断**: `git diff <マージ済みPRの先端コミット> origin/main --stat` の出力が**空**なら、このパターンだと確定できる。

**解決手順**:
```bash
git fetch origin main
git checkout -B <指定ブランチ名> origin/main   # 指定ブランチをmainの最新点から作り直す
# ここでこの増分の変更を行い、コミットする
git push --force-with-lease origin <指定ブランチ名>
```
`--force-with-lease` を使う前に、必ず上記の「診断」を確認すること。
マージ済みの履歴に含まれない未マージのコミットがブランチにある場合は、破棄せずに新しい基点の上へ載せ直す。

## 7. コミット状況を確認するstop hook

`~/.claude/stop-hook-git-check.sh` が存在する。[Hanga確認 2026-10-03]
Utsushiのセッションでは、リポジトリに有効化設定が無いにもかかわらず、コミットしていない変更が残った状態でターンを終えようとすると
「there are uncommitted changes」という趣旨のフィードバックが返ってくることが確認されている(ユーザー/グローバル側の設定で有効化されているとみられる)。[Utsushi確認]
意味のある単位の変更が完了した時点で都度コミットする運用を前提にすること。
